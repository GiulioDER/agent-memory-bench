# Context injection experiments and RE-call promotions

**Experiment date: 25 November 2026, Europe/Rome.** This report covers the 30 numbered studies with recorded outcomes that day, from 124 through 154. It also records the earlier verified-fix selector, which was already merged as an opt-in. GitHub status was checked on 26 November.

## What was promoted and when to use it

| Capability | Code and activation status | When to use it |
| --- | --- | --- |
| Normal RE-call retrieval | **On by default for ordinary retrieval.** The experiments produced no default change. | Start here for general memory retrieval and ordinary repair work. The existing retrieval and trust policy still decides what evidence can be served. |
| Regression-verified fix selection | **Merged, opt-in.** The pilot merged on 24 November and its audit fixes merged on 25 November, Europe/Rome. Invoke `recall records --repo owner/name --select-fix request.json`. | Use when a trusted runner has a shortlist of proved prior fixes, the exact pre-fix Git revision, and a way to reproduce the current failure. Ask for the shortlist, run the indicated regression on the pinned checkout, then resubmit the actual observation. The selector serves one fix only when the symptoms and diagnostic match uniquely. An active supersession excludes the retired record. [Pilot #1494](https://github.com/GiulioDER/RE-call/pull/1494) · [Audit fixes #1498](https://github.com/GiulioDER/RE-call/pull/1498) |
| Repair check selection | **Merged on 25 November, opt-in.** Invoke `recall repair-checks prompt`, `resolve`, then `feedback` with the JSON request, choices and observations. | Use after an attempted repair still fails and the runner has a small menu of runnable checks. Select one diagnostic and one preservation check. Run both on the same failed edit and give the retry their observed results. Add a prior procedure only when a distinct, citable earlier repair provides a relevant way to distinguish outcomes. Study 129 supports better check selection on the tested menus, with tied solve rates. [RE-call #1501](https://github.com/GiulioDER/RE-call/pull/1501) |
| Snapshot verification of retrieved SQLite rules | **Implemented in an open PR, opt-in.** Invoke `recall search "question" --sqlite-snapshot analytics.sqlite` or call `recall.sqlite_rules.verify_sqlite_rules(bundle, snapshot)`. | Use when relevant field notes describe physical date representation and the query will use a known local SQLite snapshot. Pass the same snapshot version the query will use. The verifier checks field existence, observes supported date formats, and omits unresolved format claims. Business meanings and units still come from the source notes. Studies 139 and 140 support this scoped use. [RE-call #1509](https://github.com/GiulioDER/RE-call/pull/1509) |
| Snapshot-verified multi-step SQLite planning | **Implemented in an open PR, opt-in Python API.** Call `recall.sqlite_planning.generate_sql_from_evidence(bundle, snapshot, generator)`. The PR is stacked on #1509. | Use for read-only questions that combine joins, cohort filters, stored codes, denominators, or multiple aggregations, when two calls to the same model are in budget. Supply trusted retrieval evidence and the exact snapshot. Use `code_fields` to allow short stored-value lists for specific categorical columns. If the plan cannot be checked, the second call receives the original question, schema and notes. The application runs the returned SQL against the checked snapshot version. Study 154 passed. [RE-call #1512](https://github.com/GiulioDER/RE-call/pull/1512) |
| Literal-only stored-code repair | **Research result published.** Available as a measured method in the benchmark. Ordinary-draft automation failed qualification. | Use the passing result to evaluate an otherwise correct draft with one bad literal and a known, independently identified edit position. The ordinary-draft test gained zero exact answers, so keep plain review as the operational baseline. [Study 151 results PR](https://github.com/GiulioDER/agent-memory-bench/pull/122) |

The two SQLite features were still awaiting merge at the GitHub check for this report. Hosted rollout remained paused. Merge status describes the repository. Availability on a particular installation depends on its installed revision, and each promoted workflow requires an explicit call.

For SQLite analytics, whole-question BM25 stayed the comparison baseline for selecting up to three field notes. The model selector improved note coverage in a small gate, then tied BM25 on exact results in both answer comparisons. This finding concerns the tested analytics workflow and its note corpus.

## CCA repair and patch selection

Joint solve means that a patch passed both the target regression and the preservation check. A check-selection gain, an added test catch, and a joint solve measure different outcomes.

| Study | Control and treatment | Result and decision |
| --- | --- | --- |
| 124 · One-bug context add-back | Original retrieval, fix only, the same-loader constraint, and a same-length unrelated note. Six runs per arm on one selected checkpoint bug. | Original **5/6**, fix only **0/6**, constraint **6/6**, unrelated **3/6**. The result motivated a holdout. |
| 125 · Across-audit constraint holdout | Ten new bugs. Nine complete paired bugs after one ungraded trial. | Original **18/18**, grounded constraint **14/18**, fix only **13/18**, unrelated **13/18**. Six original prompts already matched fix-only. The holdout supported keeping original retrieval as the baseline. |
| 126 · Repair boundary and preservation note | Seven bugs, two repeats per arm. Rewrite an already first-ranked relevant note into an explicit boundary and preservation note. | Final joint solves **8/14 in both arms**. First attempts **7/14 → 8/14**. All seven bugs tied after retry. |
| 127 · Whole-line editing and parser location | Original numbered edit format versus whole-line replacement, with parser location on eligible treatment retries. | Mechanical panel final **5/12 → 3/12**, and first rejections **7/12 → 8/12**. Matched preservation panel final **8/12 → 6/12**. The replacement format missed both directional predictions. |
| 128 · Behavioral feedback on retry | After an accepted edit failed a check, compare generic failure, observed behavioral feedback, and the same feedback with an older procedure. | Joint solves **0/10**, **3/10**, and **2/10**. Both behavioral wins came from one audit. Use actual check outcomes to describe a retry. The procedure addition had no observed benefit. |
| 129 · Select checks before retry | Choose one diagnostic and one preservation check from a fixed menu, with current evidence alone or with a prior procedure. A prevalidated pair served as a control. | Full pairs **4/6 → 6/6**. Joint solves **8/12 → 8/12**, with **7/12** for the prevalidated control. Only two bugs received changed repair prompts. The bounded check-selection workflow was promoted as opt-in. |
| 130 · Natural candidate pool | Run 28 sealed patch-generation requests across seven bugs. Grade accepted candidates before running a selector. | **23** valid edits and **20** distinct patches. Only **1/7** bugs had a passing and a plausible wrong candidate under the original grader, versus **4** required across three audits. The selector sent zero requests. Study 131's independent time assertion rejected the apparent pass on that sole mixed bug. |
| 131 · Qualified mixed pools | Screen 16 repairs, qualify 12 fresh bugs, and build three checked candidates per bug. Compare current evidence with one prior procedure in **24** sealed selector requests. | Correct patch choices **56/72 → 53/72** across six orderings per bug. The procedure changed one of twelve check pairs and admitted an overbroad patch on some orderings. The six orderings reuse one selection per arm. The pilot showed that the legal menus could distinguish the references after correction of the time oracle. |

The earlier Study 123 repeated Task Solve control was **38/120** for both original retrieval and verified delivery with original retrieval on abstention. The verified-fix opt-in supports a narrow serve decision. The replay's measured solve rate stays tied.

## Historical requirements and external patch evidence

The external work followed the PatchDiff paper's use of behavioral differences between plausible agent patches and maintainer fixes. The study labels and independent checks helped distinguish a public test pass from a proven wrong behavior. [Wang, Pradel and Liu](https://arxiv.org/abs/2503.15223) · [PatchDiff archive](https://zenodo.org/records/17074796)

| Study | Test | Result and decision |
| --- | --- | --- |
| 132 · Executable historical requirement pilot | Run independent historical checks against six selected cases with authored wrong patches. | **4/6** added catches against named public witnesses. Nearby existing tests already caught two of the four, leaving two candidate gaps after that targeted follow-up. All six reference patches passed. |
| 133 · Fresh holdout with stronger current baseline | Compare five cases to the relevant public suites and score whether historical checks add catches. | **2/5** added catches across two audits. The planned bar was three cases across three audits. The paid comparison stayed closed. |
| 134 · External historical requirement holdout | Reproduce the published SymPy example and compare source-only with history-assisted check writing on archived patches. | The calibration check caught the wrong SymPy patch after both patches passed the named public suite. On the fresh holdout, both arms caught **0/4**, with one additional unpaired case. Every frozen check accepted its maintainer fix. |
| 135 · Wider external history search | Add the benchmark test path to the production-path search on 24 bugs. Replay two frozen tests from the wider screen. | Reviewed top-three requirement coverage **7/24 → 9/24**, with **10/24** in the union. The executable checks added zero catches. One originally rejected a maintainer patch because of an extra assertion assumption. The narrowed diagnostic also added zero catches. |
| 136 · Independently qualified external wrong patches | Qualify six of ten archived patches from Django, SymPy and xarray with independent correctness checks. Compare current source and tests with the same evidence plus older assertions. | Both arms caught **0/6** and falsely rejected **0/6** maintainer fixes. The gate required two added catches. The owner paused patch-selector context experiments after this result. |

## SQLite note retrieval and verification

Studies 137 to 146 use the financial and California schools SQLite snapshots. The initial pilot used corrected Arcwise-Plat questions. Later cohorts and per-case qualification are recorded in each study. Exact accuracy compares query results with reference results. The retrieval gates in 141 to 145 compare how often every required note fits within the same three-note budget. [Arcwise-Plat release](https://github.com/uiuc-kang-lab/text_to_sql_benchmarks)

| Study | Test | Result and decision |
| --- | --- | --- |
| 137 · Supplied business-rule context | Eight questions, same schema, model and scorer, with manually supplied reporting rules in the treatment. | Exact **3/8 → 7/8**, four gains and zero losses. Pass to automatic retrieval. |
| 138 · Automatic BM25 field notes | Eight fresh questions. Compare schema-only to automatically selected notes. Six cases had identified required notes. | Exact **1/8 → 3/8**, three gains and one loss. Complete note coverage **3/6**, below the **5/6** gate. The regression came from a relevant but stale `YYMMDD` claim on a column stored as `YYYY-MM-DD`. |
| 139 · Verify the note against the snapshot | Replay Study 138's one loss and three gains with checked notes. Replay the raw stale note as a control. | The raw prompt repeated the regression. The verified prompt fixed it and kept **3/3** gains. This was a targeted replay. |
| 140 · Fresh snapshot-verification holdout | Four fresh cases, each with schema only, raw retrieved notes and checked notes. | Exact **3/4**, **2/4**, and **4/4** respectively. Both stale-rule regressions were restored, the raw-note gain was retained, and there were zero new losses. Pass for the scoped verifier. |
| 141 · Weight field labels and aliases | Six fresh questions. Add field-label and alias scores to baseline BM25. | Complete coverage **3/6 → 4/6**. Below five, so the answer stage stayed closed. |
| 142 · Suppress near-duplicate notes | Six fresh questions. Skip redundant notes while filling the top three. | Complete coverage **3/6 → 2/6**. Gate failed. |
| 143 · Retrieve separately for each clause | Six fresh questions. Rank each question fragment separately with three total notes. | Complete coverage **1/6 → 0/6**. Gate failed. |
| 144 · Keep clauses tied to fields or entities | Six fresh questions. Retrieve for field-anchored clauses with the same three slots. | Complete coverage **3/6 → 3/6**. Gate failed. |
| 145 · Model selects fields | Six fresh questions. A model selects up to three field IDs from the database catalog. | Coverage **2/6 → 5/6**, so the answer stage ran. Exact SQL tied **5/6**, with one gain and one loss. |
| 146 · Larger model-selection holdout | 32 fresh questions, 16 per database. Same SQL writer, snapshot verification, and budget of up to three notes. | Exact **21/32 in both arms**, with three gains and three losses, exact paired **p = 1.0**. BM25 stays the baseline for this workflow. |

## SQLite draft review, literal repair and planning

| Study | Test | Result and decision |
| --- | --- | --- |
| 147 · Snapshot evidence during review | 12 fresh questions. Plain review versus review with profiles for fields selected from the question. | Exact **8/12 in both arms**, zero gains and losses. Missed the two-gain gate. |
| 148 · Profile fields named by the draft | 12 fresh questions. Derive profile subjects from the SQLite draft and compare with plain review at the same three-note budget. | Exact **8/12 in both arms**, zero gains and losses. Missed the two-gain gate. |
| 149 · Profile deliberate code and date errors | Eight seeded drafts. The reviewer can rewrite the query. | Exact **5/8 → 6/8**, two gains and one loss. The improvements came from code cases, and the zero-loss gate failed. |
| 150 · Allow only the wrong literal to change | Six fresh seeded wrong-code cases. Apply only the replacement to the designated literal. | Exact **4/6 → 5/6**, one gain and zero losses. Fell one gain short. |
| 151 · Binary qualification of literal-only repair | 12 fresh seeded cases and a supplied edit position. Pass requires at least 11 exact, two gains and zero losses. | **PASS.** Exact **9/12 → 12/12**, three gains and zero losses. All 12 changes were applied within the allowed position. The published result qualifies this controlled repair setup. [151](../preregistration/151-literal-only-code-qualification.md) · [Results PR](https://github.com/GiulioDER/agent-memory-bench/pull/122) |
| 153 · Detect and repair ordinary drafts | 20 fresh unseeded drafts. Require two gains, zero losses and zero triggers on correct drafts. | **FAIL.** Exact **19/20 → 19/20**, zero gains, losses or triggers on correct drafts. The sole wrong draft's absent literal was located, but the proposed replacement was also absent and was rejected. A post-score exact-span repair using the unique stored prefix reproduced the reference for that one case. |
| 154 · Plan, verify, then write | 20 fresh multi-step questions. Draft then review versus structured plan then SQL, with the same model, two calls and up to three notes per arm. | **PASS.** Exact **14/20 → 17/20**, three gains and zero losses, clearing the two-gain gate. First drafts alone got **15/20**. The result measures the combined workflow on two snapshots. |

The saved-draft investigation between Studies 151 and 153 found one identifiable out-of-domain literal as well as drafts with multiple unknown values, stored codes used with the wrong meaning, or no SQL. It informed the detector gate. The completed record has no separately scored Study 152.
